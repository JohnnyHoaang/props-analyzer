# Supabase Integration — Phase 1: Schema + Foundations Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up Supabase as infrastructure — schema, RLS policies, generated types, `@supabase/server` install, validated env, and an admin-client module in `apps/api` — without switching any read path off the existing mock/Prisma `DataClient`.

**Architecture:** Supabase CLI manages a version-controlled SQL schema (`supabase/migrations/`) applied to a local Docker stack and, later, the hosted project. Types are generated from that schema to eventually replace the `@prisma/client` re-export. `apps/api` gains a lazily-constructed singleton service-role Supabase client, exported but wired into no service or route yet. The app continues to run exactly as before.

**Tech Stack:** Supabase CLI, Postgres (via Supabase local Docker), `@supabase/server` v1.4.1 + `@supabase/supabase-js`, NestJS 11, zod 4, Nx 23, pnpm, Jest.

## Global Constraints

- TypeScript everywhere; strict; **no `any`** (AGENTS.md).
- Every table has `id`, `created_at`, `updated_at` (AGENTS.md DB rule). No hard-deletes of production data.
- Never expose provider response objects to the frontend / convert to internal DTOs (relevant later; Phase 1 adds no routes).
- Frontend never calls Supabase directly — only the NestJS API does.
- ESM: all app/package code uses `.js` import specifiers and `"type": "module"` packages.
- **Phase 1 is non-breaking:** no service, controller, route, or existing test changes behavior. The only test file modified is `packages/configuration/src/lib/env.spec.ts` (additive).
- Env var names are fixed and already in `.env`: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, `SUPABASE_JWKS_URL`. Do not rename.
- New Postgres columns use **snake_case** (Supabase convention); the BDL importer (Phase 2) and DTO mappers (Phase 3) adapt field names — do not try to preserve Prisma's camelCase column names.
- Verify commands run from the repo root `/Users/johnnyhoang/repos/props-analyzer` unless stated.

- [ ] **Step 3: Implement `SupabaseService`**

`apps/api/src/app/supabase/supabase.service.ts`:

```ts
import { Injectable } from '@nestjs/common';
import { loadEnv } from '@props-analyzer/configuration';
import { createAdminClient } from '@supabase/server/core';
import type { SupabaseClient } from '@supabase/supabase-js';

/**
 * Singleton service-role Supabase client for server-side, RLS-bypassing
 * access (catalog reads in later phases, ingestion). Constructed lazily on
 * first `admin` access — like PrismaService, the API can boot without
 * SUPABASE_* creds; only code that actually touches Supabase requires them.
 *
 * Phase 1: provided and exported by SupabaseModule but injected nowhere.
 */
@Injectable()
export class SupabaseService {
  private cached: SupabaseClient | null = null;

  get admin(): SupabaseClient {
    if (!this.cached) {
      // Fail fast with a readable message if creds are missing.
      loadEnv(process.env, ['SUPABASE_URL', 'SUPABASE_SECRET_KEY']);
      this.cached = createAdminClient();
    }
    return this.cached;
  }
}
```
